# Wave 94 · Prepared Release SHA Stability

## Purpose

Wave 94 closes the last source-identity gap before a real BINARIO Marketing release can be physically certified and later published through the W91–W93 release chain.

Before W94, the canonical source was intentionally fail-closed (`0.9.0.dev1`, `RELEASE_READY=False`, `RELEASE_TAG=None`) while physical UAT evidence was bound to the exact main Git SHA and source digest. A future release would eventually need a stable version, `RELEASE_READY=True`, and a canonical tag. If those source bytes were changed **after** physical UAT, the release commit would no longer be the exact commit that had been physically tested. The security controls would then be forced to choose between stale evidence and a new untested SHA.

W94 removes that contradiction by defining a source-preparation state that exists **before** physical UAT but grants no operational or publication authority.

## Canonical source states

### `LOCKED_SOURCE`

The current repository remains in this state:

- development/RC version is allowed;
- `RELEASE_READY=False`;
- `RELEASE_TAG=None`;
- source is not release-ready;
- physical UAT may be used for product validation;
- evidence produced from this state can never satisfy a future production release gate.

### `PREPARED_RELEASE`

A future dedicated source-preparation commit may enter this state only when all three source facts are coherent:

- version is stable, not dev/alpha/beta/RC;
- `RELEASE_READY=True`;
- `RELEASE_TAG == v<version>`.

`PREPARED_RELEASE` means only that release intent has been frozen into one exact source commit **before** physical UAT. It does not grant any of the following:

- operational authorization;
- release authority;
- publication authority;
- production readiness;
- Developer ID signing;
- Apple notarization;
- GitHub Release publication.

Any mixed or partial state is invalid rather than being silently interpreted as either state.

## Exact candidate origin

The exact physical-UAT candidate remains arm64-only and is trusted only when generated by a controlled GitHub Actions `push` to `refs/heads/main`.

A tag build is never an exact physical candidate. Tags continue to produce source-equivalent distribution rebuilds under the W88+ contract.

This keeps two identities separate:

1. **physical candidate** — exact main arm64 bundle tested by a human on a real non-CI Apple Silicon Mac;
2. **distribution rebuild** — Developer-ID-signed/notarized native build reconstructed from the exact same source commit at tag runtime.

## W94 evidence binding

The W94 source contract is propagated through the physical-UAT chain without changing historical runtime/certification identities:

- runtime remains Wave 76;
- physical candidate guard remains Wave 84;
- combined UAT attestation remains Wave 85;
- source-contract guard is Wave 94.

The following evidence now carries and verifies `source_contract_wave=94`, `source_release_state`, and `source_release_tag`:

- `PHYSICAL_UAT_CANDIDATE.json`;
- `FULL_MAC_DELIVERY.json`;
- operator handoff verification;
- Phase B `release-uat-evidence.json`;
- each manual Phase B update;
- combined physical-UAT attestation.

Existing evidence cannot be resumed across a different source-contract generation, state, tag, SHA, source digest, or candidate-manifest digest.

Legacy combined attestations remain diagnostically readable as `LOCKED_SOURCE`, but cannot be upgraded into `PREPARED_RELEASE` evidence.

## Release lifecycle after W94

A future real release must follow this order:

1. Create a dedicated source-preparation change that sets a stable canonical version, `RELEASE_READY=True`, and `RELEASE_TAG=v<version>` in one coherent commit.
2. Certify and merge that exact commit to `main`.
3. Build the arm64 exact physical candidate from the resulting `main` push.
4. Execute Phase A physical product UAT on a real non-CI Darwin arm64 host.
5. Execute all 12 Phase B release-operational gates with concrete observations.
6. Finalize the combined UAT attestation. It must bind the exact SHA, source digest, candidate manifest, stable version, `PREPARED_RELEASE`, W94 source-contract generation, and future tag.
7. Create the canonical version tag pointing to **that same commit**, with no source mutation after UAT.
8. Tag preflight verifies the transported combined attestation against exact `GITHUB_SHA`, `PREPARED_RELEASE`, and `GITHUB_REF_NAME`.
9. Native arm64/x86_64 source-equivalent distribution rebuilds are Developer-ID signed, notarized, and production-gated.
10. W92 verifies the packaged ZIP round trip and Apple trust after packaging.
11. W91 verifies exact release evidence and produces cross-architecture authorization.
12. W92 produces artifact publication authorization.
13. W93 performs the fail-closed GitHub Release draft transaction, downloads and verifies exact published bytes/inventory, and only then publishes the release.

No later step may repair or reinterpret an earlier source identity mismatch.

## Intel certification compatibility

The persistent-release PR smoke previously hardcoded `0.9.0.dev1`. That would reject the first legitimate stable prepared-release PR even if all other contracts were correct.

W94 changes the Intel current-runtime certification to compare packaged provenance against the canonical `binario_marketing.version.__version__` dynamically. Runtime remains Wave 76; only the stale version literal is removed.

## Source-only readiness

`evaluate_release_readiness()` now distinguishes source preparation from production authorization:

- coherent `PREPARED_RELEASE` with no operational inputs → `SOURCE_CONTRACT_READY`, `production_ready=false`;
- explicit Developer ID + notarization + UAT facts are still required before the evaluator can describe production readiness;
- the source enablement audit itself never claims external runtime facts or authority.

This prevents a stable version flag from becoming an accidental publication capability.

## W91–W93 preservation

W94 is additive. It does not remove or weaken:

- W91 exact per-architecture release evidence and cross-architecture authorization;
- W92 packaged artifact round-trip trust and artifact publication authorization;
- W93 transactional GitHub Release draft/upload/download/final-inventory verification and fail-closed cleanup.

The W94 checks occur before those layers and are rechecked before final authorization/publication.
